# design · T-20 看板重构综合方案（分析现状 + 综合方案）

> 模板来源：`dev-work/templates/TEMPLATE_DESIGN.md`。本文件 = T-20 的**综合方案**（分析 + 设计），供老板闸1 签核后转实施。
> 铁律：无输出 = 未测 = 不通过。本节为方案设计（非实现），自测证据在实施阶段填。

---

## 〇、老板两大方向（需求锚点）

1. **执行任务的标准地方**：看板必须是团队（阿编 + agents）执行任务的**唯一标准面**——拉任务、推进状态、留痕都在这里，不再"另一套 md 也维护"。
2. **看进站和堵塞**：老板一眼看到「进站」（新进 / 排队 / 积压）和「堵塞」（卡住 / 受阻 / 依赖 / 超时）。

> 注：老板要的是**任务视角**的进站/堵塞，不是另造一套业务 KPI（出片数/营收）。方案据此设计，避免范围膨胀。

## 一、现状分析（已查实事实）

| 项 | 实测值 | 含义 |
|---|---|---|
| 服务 | 8787 / 8788 均 LISTENING | 门户+看板都在跑，非"没建" |
| board.db 规模 | projects 3 / tasks 22 / presence 3 / audit 26 / notes 3 / milestones 7 | 有数据，非空 |
| 任务状态分布 | **完成 10 / 待办 12 / 进行中 0 / 待验证 0 / 已验证 0** | **在途恒为 0 → 老板看来像死数据** |
| 项目构成 | 「看板项目」「测试项目」(测试残留) + 「短剧自动化工作流」(阿编) | 无真实 3 工作线项目 |
| 前端 | `index.html` 标题「任务看板」，仅 kanban / tree 两视图 | 无进站/堵塞视图、无筛选/快切/留言/自动刷新 |
| API | `/api/projects` `/api/tasks` `/api/presence` `/api/audit` `/api/projects/<pid>/milestones` `/api/milestones/<mid>` `/api/ext/{status,projects,tasks,audit,presence,notes}` | 能力底座够，缺 进站/堵塞 聚合端点 |
| 技能约定 | `board` SKILL.md：5 态 + 阻塞旁路、owner 路由、X-Agent、X-Board-Token、审计、在线状态 | 机制已齐，但**没人按它喂数据** |
| DB / 服务模型 | `sqlite3.connect` **每次请求新开连接**、**无 WAL**（默认 rollback journal）；服务为**单线程 `HTTPServer`**（非 Threading） | 服务内部写入串行安全；但**任何外部进程直连 SQLite 会与服务抢锁 → `database is locked`**；看板操作为**低频状态变更**（单任务生命周期约 5–10 次跳变），非高频流 |

**结论**：看板"没用上"不是没建，是**建歪 + 没人喂 live 数据**。老板视角缺两样东西：① 一个团队真在上面跑任务的标准面；② 进站/堵塞的可视信号。

## 二、根因（老板已认可）

1. **方向错位**：8788 是「阿编内部开发任务追踪器」，老板要看的是"任务执行中台 + 进站/堵塞信号"。
2. **双系统漂移**：真实进度在 `dev-work/current_state.md`（阿编认真维护），看板喂得不一致 → 在途恒为 0。
3. **T-08b 整块没落地**：筛选 / 状态快切 / 指导留言 / 自动刷新 / 完成时间戳 / flash 全没做（08-13、08-14 方案未执行）。
4. **调度纪律没把看板当真相源（老板点名的"散/不连贯/发现晚"真根）**：`software-team-dispatch` 技能 GATE0~§7 全程不提看板，真相源写死为 `dev-work/tasks/T-XX/` + `current_state.md`；派活流程无"建卡→agent 对卡读写"，agent 只拿 md 路径、与看板脱钩 → 任务散在三处、连主理人都不确定 board 准不准、派活不连贯、问题靠事后翻 md 才发现。**这是①②③的上游根，必须 Phase 0 锁死。**

## 三、综合方案（6 块）

### 3.0 调度纪律：看板 = 唯一真相源（Phase 0 · 根治根因④，必先做）
> 老板点名："很多你目前遇见的问题都是因为放在各处自己也不知道。调度团队也没办法一直执行。发现问题。"——根在调度流程从没把看板当真相源。本块把"看板=调度唯一真相源"**写死进 `software-team-dispatch` 调度宪法**，让 T-20 的进站/堵塞视图从"空架子"变"真数据源"。

- **G0-0 派活前置建卡（无卡不派活）**：派活前必须在看板建任务卡（`POST /api/tasks`，project=对应工作线，status=待办/进站），拿 `card_id` = 任务身份证；未建卡 = 派活非法（写入 dispatch 技能 GATE0）。卡与 `tasks/<T-ID>/` 四文档互相引用（卡 detail 挂 T-ID 链接，md 顶部挂 card_id）。
- **Agent 对卡读写（卡在前）**：派活 prompt 模板把 `card_id` 前置，agent 自己 `GET /api/tasks/<card_id>` 读卡、`PUT /api/tasks/<card_id>` 推状态（待验证/已验证打在卡上），md 四文档降为"挂在卡下的深度证据"（不冲突，I-1 四文档保留）。
- **主理人看板监控**：进站积压 / 堵塞（>3 天标红）/ WIP 一眼可见，**不翻 md**；读盘核产改为"先看板卡状态 + 卡下 notes/audit，再核 md 落盘"。
- **三系统收敛为单源**：
  | 原三套 | 新定位 |
  |---|---|
  | `shared_board` (8788) | **活真相源**（状态/owner/WIP/阻塞，实时） |
  | `dev-work/tasks/<T-ID>/` 四文档 | 证据归档（派生：挂在 card_id 下，深度细节） |
  | `dev-work/current_state.md` | 审计留痕（由 board 自动派生，见 3.1 `sync_board_to_md`） |
- **实施动作**：① `software-team-dispatch` 技能加 `G0-0 看板建卡前置` + 派活 prompt 模板改 `card_id` 前置；② 本会话起所有派活先建卡；③ 进站/堵塞视图因每次派活建卡、每次推进打卡而天然有真数据 → "发现问题晚"变"实时可见"。

### 3.1 重定位：开发任务看板 → 团队任务执行中台（根治根因①②）
- **看板 = 任务唯一真相源（live status）**；`current_state.md` 降为"验收证据档案"，其「当前任务」表改为由 board API **自动生成**（新增 `sync_board_to_md.py` 读 `/api/tasks` 全项目 → 重写该表），主理人不再手工维护 live status。
- **Agent SOP 强化**（已有，落实为强制）：开工先 `GET /api/projects?owner=<我>` + 每项目 `GET /api/tasks` 拉板；每步 `PUT /api/tasks/<id>` 更新状态/详情；禁止在 md 另维护 live status。
- **兜底**：`sync_board_to_md.py` 定时（或阿编收工）执行，保证 current_state.md 永远 == board，彻底消灭漂移。

### 3.2 进站（Intake）可视（方向②）
- **「进站 / 收件箱」视图**：`status=待办` 且**未认领**（无 owner agent / 未进 WIP）的任务，按 `created_at` 排序 → 进站队列，可点开认领。
- **顶部指标条**：
  - 进站积压数（待办未认领）
  - 本期新进（近 N 天 created，N 可配，默认 7）
  - 吞吐量（近 N 天完成数）
  - WIP（进行中 + 待验证 + 已验证）
- **进站流**：最近新建任务的时间线 feed（一眼看"新进什么"）。

### 3.3 堵塞（Blockage）可视（方向②）
- **「堵塞」视图**：`status=阻塞` **或** `blockedBy` 有未解依赖 → 堵塞清单，显示：卡多久(aging 天) / 谁卡住(owner/agent) / 卡因(detail/notes) / 依赖谁(blockedBy)。
- **schema 扩展**：`tasks` 加 `blockedBy`(逗号分隔 task id) + `blocked_reason` 字段；server 端 `POST/PUT` 接受并持久化；前端可编辑。
- **超时高亮**：堵塞 > N 天（默认 3）标红，老板一眼定位卡点。

### 3.4 补 T-08b 交互（根治根因③）
- 筛选（状态 / 优先级 / owner / agent）
- 卡片状态快切（下拉直接改 status，带 owner 校验）
- 指导留言栏（接已有 `notes` 表 + `/api/ext/notes`）
- 自动刷新开关（异步轮询不打断操作）
- 完成时间戳徽章（完成态显示完成时间）
- flash 高亮定位（更新项闪一下）

### 3.5 清理垃圾项目 + 建真实 3 工作线（对齐实际组织）
- 删「测试项目」「看板项目」残留（避免老板看到测试噪音）。
- 建 3 真实项目：**生产工作台 / 配方训练线 / 协作运维基座**，任务按归属迁移，看板结构 == 实际项目结构。

### 3.6 老板首页（轻量，全派生）
- 顶部一屏汇总：进站积压 / WIP / 堵塞数 / 近期完成 —— 全部从任务数据派生（不另造业务 KPI 库）。
- 默认进入即见：进站 + 堵塞 + 在途信号，满足"执行标准面 + 看进站/堵塞"两方向。

### 3.7 看板接入方式 + 开销核实（老板点名确认项）
> 老板问："远程接入的 AGENT 和本地放看板目录两种方式；API 可能有大量开销，确认下都走 API 能好吗。" → **决策(2026-08-15)：不开发本地模式，全程 API；看板外网可达，大量云端 agent 走外网直连执行。**

**接入方式（结论：全程 API，禁止直写 SQLite，不开发本地 spool 兜底）**

| 方式 | 适用 | 机制 | 结论 |
|---|---|---|---|
| ① 云端 AGENT（外网 API） | 无本机文件权的远程/云端 agent | 经 8787 门户外网地址 `https://<外网>:8787/board/api/{tasks,ext/*}`，带 `X-Agent` + `X-Board-Token` | **主形态**：老板已有外网，可拉大量云端 agent 并行执行 |
| ② 本地 AGENT（API） | 同机 agent（阿编主进程 / 子 agent） | **也走 API**（127.0.0.1:8788 或经 8787 反代），不加本地目录兜底 | **与云端统一**：同一套调用，零分支 |
| ❌ 本地直写 SQLite | — | 直接 `sqlite3.connect(board.db)` 写 | **禁止**：服务单线程 + 无 WAL，外部直连会抢写锁 → `database is locked`、甚至库损坏 |

**开销核实（老板核心顾虑：全走 API 扛不扛得住）—— 已实测(2026-08-15)**

> 实测环境：8788 在跑(PID 32924) / Windows / 单线程 `HTTPServer` / 无 WAL；N=200 连续写取平均。
>
> | 模式 | 单次写延迟 | 相对 | 备注 |
> |---|---|---|---|
> | API（PUT `/api/tasks/<id>`） | **1.60 ms/op** | 基准 | 写入即生效，**实时可见**（满足"看进站/堵塞"） |
> | 本地 spool（写目录·仅参照，不开发） | 0.20 ms/op | 快 8x | 仅省 1.4ms，但**延迟可见**需 drain 才进看板——舍弃 |
> | SQLite 直连（生产禁止·参照） | 6.09 ms/op | 最慢 | 抢锁 + fsync 偏慢，**彻底否决** |
>
> **差距量化**：本地目录比 API 只快约 **1.4 ms/op**（8x），两者都亚 2ms。看板是低频状态变更（单任务 5–10 次跳变、全天百次级），1.6ms 对人类无感、对系统零压力。**"为性能上本地模式"不成立**——本地模式仅省 1.4ms 却牺牲老板要的"实时可见"，故不开发。

- **结论：全程 API 完全扛得住，开销可忽略。** 理由：
  1. **低频**：看板只承载"状态变更"（待办→进行中→待验证→已验证→完成 + 偶发 notes/audit），单任务生命周期约 5–10 次写；即便数十云端 agent × 数十任务 ≈ 千次/天，对 HTTP 属零负载。
  2. **延迟**：回环 ≈ 1ms/请求（外网多几十 ms，仍可忽略），服务单线程串行处理，对本量级永不成为瓶颈。
  3. **唯一禁忌**：**不要把高频流（逐秒心跳 / 日志喷涌）灌进看板 API**。心跳/日志仍走本地文件与既有通道；看板只存"状态"，不存"遥测"。守住这条，API 永无开销问题。
- **服务可用性靠常驻部署保障（替代本地兜底）**：不开发 spool 目录兜底；看板服务保持常驻 + 自启（已沉淀的 8787 门户 + 自启机制），外网可达即云端 agent 可写。若偶发服务不可达，agent 侧 `board_client.py` 仅做短时重试/报错，不落本地目录（避免数据分叉后难回收）。

### 3.8 文档/资产传输通道 + 统一文档库（老板点名·远程 agent 拿素材的断点）

> 老板问："需求文档怎么传输？本地你们自己还好，远程的怎么办？他怎么把文档传输过来？是不是建一个总的文档库？" → **决策：建统一文档库，全程 API 传，不开发本地落盘；本地与远程 agent 同一套调用。**

**现状断点（已查实 server.py / agnes_proxy.py）**
- 看板 server.py（8788）只有**状态 API**（JSON tasks/notes/audit），**零文件端点**（无 upload/download/multipart/blob）——只传状态、不传素材。
- 8787 门户已有"远程取资产"成熟范式：`/batch/__asset__/<batch>/<kind>/<name>` → 磁盘白名单 + 纯 ASCII URL + 反代外网（T-18 验证可用）。但那是**训练专用大图**，不是通用文档库。
- 结论：远程 agent 现在能打卡、**拿不到任务素材（PRD/剧本/分镜/参考图/交付物）**。"全程 API"若只传状态不传文档，远程 agent 接了卡也干不了活——这正是老板点出的断点。

**方案：统一文档库（轻量自建 / API 化 / 不碰 SQLite 存大文件）**

- **物理**：`shared_board/docs/<doc_id>/<file>` 磁盘目录存文件；DB 新增 `docs` 表只存**元数据**（doc_id、task_id、owner、文件名、大小、mime、sha256、created_at），**绝不存 blob** → 不膨胀 SQLite、不抢锁。
- **端点**（挂在 8788 看板，复用现有 `X-Agent`+`X-Board-Token` 鉴权）：
  - `POST /api/ext/docs`（上传：raw body 或 multipart + `?task_id=` + token）→ 落磁盘 + 写元数据，返回 `doc_id`
  - `GET /api/ext/docs/<doc_id>`（下载：流式返回文件）→ 经 8787 `/board` 反代外网可达（**复用既有 `/board/api/`→8788 替换逻辑，零新增路由**）
  - 任务卡 `GET /api/tasks/<id>` 响应里带 `documents: [doc_id...]`；主理人派活时先把素材传库、卡挂引用
- **本地 agent**：同机也走 API（127.0.0.1:8788 或 8787），全程 API 一致（呼应 3.7 决策"不开发本地模式"）。
- **远程 agent（外网）**：`GET https://<外网>:8787/board/api/ext/docs/<doc_id>` 拉素材；`POST .../docs` 回传交付物（代码/报告/图）→ 主理人/老板外网也能看。

**与训练线资产路由的关系**：并存不替代。`/batch/__asset__/` 留给训练专用大图（候选/参考）；通用任务文档（PRD/剧本/分镜/交付物）走文档库。两者都走 8787 反代、都纯 ASCII 路径、都不碰 SQLite blob。

**要不要"总的文档库"：要，且必须是统一一个**（按 doc_id 跨任务/跨项目索引），不是每任务各建目录——否则又回到"散落"老路。物理按 task_id 分目录便于清理，逻辑上全局索引。

**约束（关键）**
- 8787 公网可达无鉴权（D4 前提破产已记），文档库走同门户 → 文档也暴露公网。**缓解**：端点强制 `X-Board-Token` 校验（已有机制），远程 agent 用 token 而非裸访问；敏感文档（未公开剧本/金配方）建议脱敏或仅本机访问。
- 看板单线程，大文件上传会短暂阻塞其他打卡请求几秒——文档库低频可接受；若后续大文件频繁，拆独立端口服务。

### 3.9 尚未覆盖的盲点（架构级 · 老板点名"再想想"）

> 在 F1~F8 / 3.0~3.8 之上，站在"全程 API + 远程云端 agent + 统一文档库 + 调度纪律"架构推演，仍存在以下未覆盖项。按对架构硬度的影响分级，**P0 必须在实施前定方案，否则整件事有硬伤**；P1 在 Phase 2 或后续；P2 为优化。

| 级 | 盲点 | 当前方案缺口 | 对老板的影响 | 建议处置 |
|---|---|---|---|---|
| **P0-1** | **泄密面**：8787 公网无鉴权 + 文档库仅共享 `X-Board-Token` → 剧本/金配方等核心资产裸奔；token 分发即泄露面；无"谁下载了什么"审计 | AC-8 只验"能传能下载"，无项目级权限、无 agent 溯源、无下载日志 | 商业机密外泄风险（短剧剧本=命根子） | 文档库端点加**项目级权限**（token 绑 owner/project）+ **下载审计**写 audit 表；未公开剧本默认仅本机/脱敏 |
| **P0-2** | **单点故障无降级**：砍 spool 后，看板/8787 挂=全员（含所有云端 agent）立即停工，无监控/自愈/告警 | 3.7 仅"常驻+自启"一笔带过 | 服务挂了没人知道、云端 agent 全停、任务卡死 | 加**可用性探活 + 自启 + 老板/主理人告警**（飞书）；agent 写失败按"重试上限→报错→任务挂 blocked"而非静默丢 |
| **P0-3** | **状态模型不全 → 看不准**：缺 排队已认领未开工 / 等待外部(等老板拍板/等第三方) / 返工被打回 / 暂停取消 | 仅 5 态 + 阻塞 | 老板看进站/堵塞时，僵任务归类错 → "看不准" | 状态机扩含 排队中/等待外部/返工/已取消；取消走**软删除**(保留历史，不物理 delete) |
| **P0-4** | **纪律仅有软约束**："无卡不派活"目前只靠技能/提示词，主理人/agent 理论上可绕过直派 | 3.0 写进 G0-0 但无强制载体 | 真相源可能不全，回归"散在各处" | **本地标准落地（非系统硬卡）**：①`software-team-dispatch` 技能 G0-0 内嵌"派活前须建卡"；②新建 `dev-work/调度公约.md` 明文标准（看板=真相源/无卡不派活/状态流转），跨会话可查；③派活 prompt 模板强制引用公约 + card_id 前置；主理人自身 SOP 首步即建卡。**git pre-commit / API 前置硬卡降为可选 P2 增强**（不强制，避免误伤正常提交与 agent 调用复杂度） |
| P1-1 | **文档库技术债**：大文件(视频/大图)超时/无分片续传；无版本(agent 缓存旧文档干活)；无清理 TTL；无文件类型校验(.exe 中毒风险)；无去重 | 3.8 只建基础库 | 大资产传失败 / 干错活 / 库膨胀 / 中病毒 | 大文件走分片+续传；doc 带 version/ETag；定期清理策略；mime 白名单；相同 sha256 去重引用 |
| P1-2 | **远程 agent 身份/信任**：`X-Agent` 头任意填、无注册白名单、无速率限制 | 3.7 假设都可信 | 恶意 agent 混进来刷屏/传毒/写假进度，无法溯源 | agent 注册 + token 绑身份；速率限制；上传文件类型/大小校验 |
| P1-3 | **双写一致性**：建卡+传文档+挂引用是 3 个独立调用，半吊子状态(卡建了文档没传/引用没挂) | 3.8 未定义原子性 | 远程 agent 拉到 404 / 不知道有文档 | 引入"素材就绪"状态机：素材未就绪卡不可派 / agent 不可开工 |
| P1-4 | **移动端 + 主动通知**：老板大概率手机看，看板 8788 移动适配未验；堵塞标红但无推送 | 3.6 仅看板内显示 | 老板不刷页面就看不到堵塞 | 看板移动端适配(T-19 已做手机不固定头，复用)；堵塞超阈值推飞书/微信 |
| P2-1 | **与飞书/日报关系**：看板=唯一真相源后，飞书同步+日报是否变派生？防三套并行 | 未定义 | 团队仍翻 md/飞书 → 看板不权威 | SOP 明确：看板一手、md 自动派生、飞书=推送渠道(只读) |
| P2-2 | **L1 真测缺口**：文档库需真·远程外网 agent 跑通；且需越权安全测试(A 项目 agent 读 B 项目文档应拒) | AC-8.4 可能退化为本地模拟 | 远程真链路没验证就上线=埋雷 | 强制 1 次真外网 agent L1；加越权 AC（跨项目读应 403） |
| P2-3 | **带宽/门户稳定性**：8787 是命根子，家宽上行受限传大交付物慢 | 未提 | 远程拉大文件慢 / 门户挂全停 | 8787 监控+告警；大资产走对象存储/CDN 而非经门户 |

> 处置原则：**P0 四项必须在 Phase 0/1 实施前定方案并随首期交付**（尤其 P0-1 泄密面、P0-2 可用性，属于"不做会出事"）；P1 随 Phase 2；P2 后续。本 design 仅列盲点，具体实现细节在实施阶段填 test/acceptance。
