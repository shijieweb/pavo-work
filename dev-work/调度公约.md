# 调度公约（本地标准）

> 本文件是「看板 = 团队任务唯一真相源」的明文标准，跨会话可查。
> 与 `software-team-dispatch` 技能 G0-0 同源，互为印证。派活 prompt 必须引用本公约。
> 制定：2026-08-15（T-20 设计阶段，响应老板"纪律用本地标准落地"决策）。

## 一、总纲
1. **看板是唯一真相源**：任务状态以看板（8788 / 外网 8787/board）为准，`dev-work/tasks/T-XX/` 四文档降为"证据归档"，`current_state.md` 的当前任务表由看板**自动派生**。
2. **不直连 SQLite**：任何 agent（本地/云端）一律走 API，禁止 `sqlite3.connect(board.db)`（抢锁崩库）。
3. **全程 API**：本地 agent 走 127.0.0.1:8788，云端 agent 走外网 8787/board 反代，同一套调用；不开发本地目录模式。

## 二、派活纪律（G0-0：无卡不派活）
- 派活**第一步**必须在看板 `POST /api/tasks` 建卡，拿 `card_id` = 任务身份证。
- **未建卡 = 派活非法**（技能级约束 + 本公约明文，非系统硬卡）。
- 卡与四文档互相引用：卡 detail 挂 T-ID 链接，md 顶部挂 card_id。
- 主理人自派也须先建卡，无例外。
- 派活 prompt 固定前置句：`「本任务看板卡号 card_id=<id>，开工/推进/完成均须 PUT /api/tasks/<id> 打卡，未打卡=未执行。」`

## 三、状态流转关系（当前 5 态 + 扩展态）

### 当前 5 主态（board SKILL.md 定义）
```
        派活建卡
           │
           ▼
    ┌─ 待办（进站/未认领）─────┐
    │                         │ 有人接 / 开工
    │                         ▼
    │                  进行中（在途WIP）
    │                         │ 研发干完，推此即停
    │                         ▼
    │                  待验证（研发停手）
    │                         │ 测试独立验收，推此即停
    │                         ▼
    │                  已验证（测试停手）
    │                         │ 主理人把关
    │                         ▼
    │                  完成（放行）
    │                         │
    └─────────────────────────┘

    任意态 ⇄ 阻塞（旁路态，可提交；解除回原态）
```
- **在途口径（WIP）** = `进行中 + 待验证 + 已验证`（老板首页"在途"指标据此算）。
- 这 5 态 + 阻塞 完全对应铁律：**研发推待验证即停 / 测试推已验证即停 / 主理人标完成**。

### 扩展态（P0-3 待实施，使看板"看准"）
| 扩展态 | 含义 | 与"阻塞"的区别 | 对老板视图的影响 |
|---|---|---|---|
| 排队中 | 已认领但还没动手 | 正常过渡，非异常 | 进站视图里从"未认领"移出、计入在途 |
| 等待外部 | 等老板拍板 / 等第三方 API / 等素材 | **已知计划依赖，不标红**；只显示"在等谁" | 堵塞视图里归入"等待中"（灰），不计入异常堵塞 |
| 返工 | 主理人/测试打回 | 主动退回，非卡死 | 回到进行中，堵塞视图不计 |
| 已取消 | 中止任务 | 软删除保留历史，不物理删 | 不计入在途/堵塞，但历史可追溯 |

> **关键区别**：`阻塞` = 出意外卡住了（标红告警，要老板介入）；`等待外部` = 已知的、计划的依赖（不标红，只显示"在等谁"）。二者不可混为一谈，否则老板看到的"堵塞"是假的。

## 四、agent 接活标准动作
1. `GET /api/projects?owner=<我>` 取我的项目。
2. `GET /api/tasks?project_id=<id>` 拉任务树，按优先级（紧急>高>中>低）从高到低。
3. 先做高优先级；开工即 `PUT` 改状态为进行中。
4. 每完成一步主动 `PUT` 更新状态/详情（审计自动记录）。
5. 不必显式"认领"，访问即被记录；定时回报进度。

## 五、主理人把关
- 研发推「待验证」即停 → 派 QA 做 L1 真测 → 测试推「已验证」→ 主理人读盘核产 → 标「完成」。
- 研发/测试分离铁律：开发推待验证即停、测试推已验证即停、主理人把关标完成，**三方各守一态不越权**。

## 六、与其它标准的关系
- 本公约是"调度纪律"层；`执行流程.md` 是"接任务第一步"；`主理人守则.md` 是"把关不变量"；`software-team-dispatch` 是"派活执行 SOP"。四者一致，冲突以本公约 + 执行流程为准。
- 看板改造（T-20）实施后，`current_state.md` 当前任务表改为自动派生，不再手工维护——消除双系统漂移。

## 七、B 角色需求阀门追问纪律（立项前置 · 主理人包装）

> 固化自老板 2026-08-16 决策：「B 角色追老板时，主理人先给推荐+理由、再用交互框让老板选」。
> 这是「引导问题纪律」与 B 角色（requirement-clarifier）的合体，列为立项前置标准动作。

1. **任何新需求立项前，先过 B 角色**（requirement-clarifier）：基于 8 维度追出缺失项。
2. **主理人禁止直接把 B 的问题甩给老板**（冷冰冰甩问 = 违反本纪律）。
3. **主理人标准动作（4 步）**：
   - ① 读 B 追出的缺失维度；
   - ② 按「闭环 + 有效」两问做分析，**给推荐 + 理由**；
   - ③ 用**交互提示框**（选项卡片，老板点选或自填）呈现，不堆文本；
   - ④ 老板选定后回灌 B，B 继续收敛直至 `ready`。
4. **B 是阀门挖需求，主理人是决策引导者**：分工不混——B 问清"缺什么"，主理人给清"怎么选"。
5. 本纪律与 `requirement-clarifier` SKILL.md §八、运行手册 §13 一致。
