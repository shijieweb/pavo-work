# 需求澄清角色 B（追问 / 分解 / 澄清官）设计稿

> 状态：设计稿（老板 2026-08-15 定调，待试点/立项固化）
> 来源：老板指出协作链缺"通过我的问题分析各维度→追问我→问清则一遍过、问漏则执行偏"的角色；经两轮对齐确认 B 为质量链最上游阀门（B > A）。

## 一、定位
- B 是**需求侧的上游阀门**，决定后续所有执行质量的上限。
- 职责：接老板模糊诉求 → 分析各维度 → 结构化追问 → 问清则决策/写需求一遍过；问漏则执行偏差、反复返工。

## 二、因果链（老板原话模型化）
```
老板一句模糊诉求
      │
      ▼
[B 角色] 分析出各个维度 → 结构化追问老板
      │
      ├─ 追问得详细/完整 ──► 决策+写需求 一遍过 ✅
      └─ 追问得潦草/缺维度 ──► 执行偏差、反复返工 ❌
```

## 三、8 维度框架（自动跑，只追缺失的）
| 维度 | B 要追问的本质 | 已明确则跳过 |
|---|---|---|
| ① 真实意图 | 要的是"功能"还是"功能背后的业务结果"？ | 已说清要什么结果 |
| ② 范围边界 | 做哪、不做哪、边界在哪？ | 范围已界定 |
| ③ 硬约束 | 技术/成本/时间/合规死线？ | 无硬限制 |
| ④ 验收标准 | 什么算"一遍过"？ | 有可量化判定 |
| ⑤ 与现有系统关系 | 新建/改造/接入已有（看板↔流水线等）？ | 关系已明 |
| ⑥ 风险代价 | 做错最坏怎样、能否回滚？ | 低风险 |
| ⑦ 决策权 | 哪些你拍、哪些要我推荐？ | 已指定 |
| ⑧ 节奏 | 这次做到哪、留什么后续？ | 一次到位 |

**精髓**：不把 8 个全问（那是骚扰），自动判定哪几个缺失/模糊，**只追那几个**。

## 四、工作法
接话 → 反推真实意图 → 跑维度清单 → 仅追缺失维度 → 综合成结构化需求骨架 → 交付阿编写 PRD（目标一遍过）。

## 五、与 A（质疑官）的关系
- **B 必做**（上游阀门，强制前置）。
- **A 降为后置横补**：B 铺开维度后，A 对需求骨架做横向压力测试（找 B 未覆盖的盲点/隐含假设/风险）。
- 即：先 B 深挖、后 A 横补，不本末倒置。

## 六、落地形态（推荐·轻量）
- 主理人接任何需求时**自觉跑 B 维度+追问**，不每回起独立 agent（避免拖慢主线）。
- 试点跑顺后，固化进 `software-team-dispatch` 立项前置门 + `运行手册` 新增一节。
- 后续可评估：是否有成熟开源"追问/澄清"项目可改造接入（见对比调研报告）。

## 七、机制选型（综合 7 候选 · 最值得参考的机制）

> 来源：`需求澄清角色B_开源对比调研.md` 第七、八节。结论：单克隆不够，博采众长合成。

B 角色落地时逐条实现的机制清单（标注来源，便于对照）：

| 机制 | 实现要点 | 来源候选 |
|---|---|---|
| 追问节奏 | 一次一问 + 已答跳过 + 边界封顶（≤10 问 / ≤3 轮） | prd-maker / idea-harness |
| 维度处理 | 8 维只追缺失；缺失但不重要→填默认并标 **(assumption)** | prd-maker |
| 深度控制 | follow_up_depth 旋钮 + **挑战假设问"为什么"**（戳破隐含假设） | interview-agent |
| 自适应 | 检测老板技术水平→用业务语言提问、技术维降权 | prd-maker |
| 产出物 | 需求简报 + **决策日志 + 风险登记 + 待确认问题**（md 7 段） | interview-agent / prd-maker |
| 质量闸 | 结构 linter 校验 + 5 维 rubric ready 门（模糊度<阈值才放行） | prd-maker / requirements-agent / dev-deep-interview |
| 状态机 | gathering→needs-precision→blocked→ready，Ready 才交付简报 | idea-harness |

**推荐底座**：以 idea-harness 状态机为骨架（MIT 零依赖、克隆即用），叠加上表 Tier1 机制合成 `requirement-clarifier` skill，固化进 `software-team-dispatch` 立项前置门。
