## 1. 背景与真实意图
- 多 Agent 在不同机器上协作，完成「**提问 → 出方案 → 互相评审 → 合并方案**」工作流，最终产出**老板认可**的一套方案。
- 老板（主持人）用 `/命令` 控节奏；多个 Agent 按 `seq_num` 顺序发言、质疑、合并。

## 2. 范围边界（做 / 不做）
**做**
- 提问 / 出方案 / 互评 / 合并 四阶段
- 网页端（boss）+ API（agent）双接入
- 文档 Markdown 上传 / 下载 / 合并
- 按 `seq_num` 串行控制（提问/质疑）

**不做（本期 / MVP）**
- WebSocket（纯 HTTP 轮询）
- 持久化（聊天内存存、文档落盘，重启丢聊天记录）
- 鉴权（见 G4：仅本机/内网，不加 token）
- 多轮评审（默认一轮）
- 结构化"认可"判定（见 G1：boss 手动确认）

## 3. 硬约束
- 自研轻量 **Flask 单体**（本地）
- agent 数量：**最少 2 个、无上限**（G2，编排须泛化为 N，不写死 A↔B）
- **无中立角色**：合并由某 agent 兼任"文书"（不替 boss 决策）
- 合并引擎 = **LLM agent**（G3，覆盖原 D7"不调 LLM"）
- 部署 = **仅本机 / 内网，绝不上公网**，故不加鉴权（G4）
- 网页端给 boss、API 给 agent（D4）

## 4. 验收标准（MVP）
- 主链路：`boss 建会` → `≥2 agent 经 API 提交方案` → `合并 agent(LLM) 出合并稿` → **`boss 手动确认`即终**。
- "认可" = boss 肉眼确认合并稿；**不强制**打分 / 投票 / 裁决（G1，沿用 v1.1）。

## 5. 与现有系统关系
- 独立新项目，未来独立 GitHub 仓库（**待老板提供地址**）。
- 复用 `requirement-clarifier`（B 角色立项前置门）+ 现有云 LLM API（agent 出方案/合并调 LLM）。

## 6. 风险与回滚
- **R1 并发写竞态**（多 agent 并发 POST）→ assumption：MVP 单会议实例 + Flask 加锁/单线程，不追求高并发。
- **R2 串行控制信号脆弱**（"问完了"消息丢失→死锁）→ assumption：依赖 seq_num + "问完了"，v2 加固（超时 / 显式阶段确认）。
- **R3 本地/内网部署** → 已规避公网冒名风险（G4）；若未来上公网必须补 token（回填 v1.1 TODO）。
- **回滚**：需求文档独立可改；代码未写，无回滚负担。
